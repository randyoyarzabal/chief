# Chief v3.2.1-dev Release Notes

## 🚀 What's New

### Live progress: no more repeated step lines

- Fixed: in an interactive terminal, every step that ran a command (for example in `chief.release_publish`) printed a job notice such as `[1] 47485`. That left the step's "running" line behind, so each step appeared twice. Step commands now start from a short-lived subshell, so the shell no longer prints job notices and each step shows as one line.

### Spinner rebuilt on the core progress helper

- `chief.etc_spinner` now runs on a new core spinner (`__chief_spin`), with the same arguments (`<message> <command> <output_variable>`). Changes you'll notice:
  - New default look: a smooth spinner in front of the message, like the step progress. `--legacy` keeps the original look, `message [|]` turning through `| / - \`, at the original pace.
  - No more `[1] 12345` job notices or leftover spinner text (for example the `Loading SSH keys... [|]` that could stay on screen at start-up).
  - Returns the command's exit code (it used to always succeed), so `if chief.etc_spinner ...; then` works.
  - Output containing quotes (`it's`) is captured correctly; it used to break the result.
  - An `exit` inside the command no longer exits your shell.
  - No animation when output isn't a terminal.
- Chief's own start-up, `chief.ssh_load-keys` and the update check use the core spinner directly, so they keep working even if you turn off the `etc` plugin (`chief.plugin disable core.etc`).
- Documented for plugin authors: "Progress Indicators" in docs/plugin-development.md covers the spinner (one command) and the step progress helpers (several steps, with `✓` / `↷` / `✗`, questions, `--dry-run` and a summary), with examples. The old example there passed a process ID to the spinner, which never worked; it's replaced.
- Tests: the spinner's output, exit code, quotes, the `chief.etc_spinner` wrapper, `--legacy` (all four frames), and no job notices at a real interactive prompt.

### Update branch follows your checkout ("auto")

- New default `CHIEF_CFG_UPDATE_BRANCH="auto"`: Chief updates from whatever branch its own checkout is on. Moving between stable and development is just `git -C ~/.chief switch dev` (or `main`), with no config change. On a tag or detached HEAD, `main` is used.
- The banner's `tracking:` line and the start-up hint follow it too, marked `auto` (for example `tracking: dev (bleeding-edge, auto)`), and the hint shows the command to switch.
- A branch name still pins it, as before: `chief.config-set update_branch main` (or `dev`, or any branch); `chief.update` then offers to switch the checkout back if it differs. `chief.config-set update_branch auto` returns to following the checkout.
- The installer sets `auto` (so installing from `dev` follows `dev`) instead of writing the branch name.

### Reminder when Chief's files changed since your shell loaded them

- The banner (start-up, `chief.help`, `chief.status`) now notes when the Chief version on disk differs from the one your shell loaded, for example after switching branches by hand, a `git pull`, or an update from another terminal: *"~/.chief is now v3.2.0, but this shell loaded v3.2.1-dev. Run: chief.reload"*. Silent when they match.
- The branch-switching instructions (README, getting-started) now include `chief.reload`.

### `chief.config-set` says when a change needs a new terminal

- Some settings are applied only when a terminal starts, so changing them with `chief.config-set` appeared to do nothing, with no explanation. For example, `chief.config-set prompt true` reloaded Chief, but the prompt didn't change.
- `chief.config-set` now ends with a yellow **Note** for those settings:
  - **The prompt and ls colors** (`PROMPT`, `COLORED_PROMPT`, `GIT_PROMPT`, `SHORT_PATH`, `COLORED_LS`): open a new terminal. `chief.reload` doesn't re-apply them either.
  - **`ALIAS`:** the new alias works now, but a previous alias's commands stay until a new terminal.
  - **`BANNER`, `HINTS`, `AUTOCHECK_UPDATES`, `BASH_WARN`:** you'll see the change in the next terminal.
  - **`SSH_LOAD_KEYS`, `SSH_KEYS_PATH`:** used at start-up and by `chief.reload`; `chief.ssh_load-keys` loads keys now.
- For those settings `chief.config-set` also skips its reload: a reload can't apply them, so it would only print a screen of plugin output for nothing. You get the confirmation and the note. `ALIAS` still reloads, because that's what makes the new alias work right away.
- Settings that apply right away (for example `MULTILINE_PROMPT`, plugins, editors) get no note and reload as before.
- `chief.reload -?` no longer claims to reload "color schemes and prompts"; it lists what needs a new terminal instead.
- Docs: a "When a change takes effect" table in `configuration.md`.
- Tests: `tests/config-defaults-tests.sh` runs `chief.config-set` against a throwaway config. It checks that `prompt` and `ssh_load_keys` get the note and no reload, and that `multiline_prompt` gets no note and does reload.

### Secrets: `--quiet` for load and edit

- `chief.secrets_file-load` and `chief.secrets_file-edit` take `-q` / `--quiet`: no "Success" or progress lines ("Secrets file loaded", "re-keyed", "Creating new secrets file", "Saved password updated"). Errors and warnings still show, for example a wrong password or a password file that still holds an old password, so a failure is never silent.
- With `chief.secrets_file-edit --load --quiet`, the quiet flag carries over to the load.
- Handy at login: `chief.secrets_file-load --quiet` in `~/.bash_profile` loads your secrets without printing anything.
- Tests: quiet load prints nothing but still loads, errors still show with `-q`, and a quiet `--rekey` hides its success line but keeps the password-file warning.

### Secrets: save a file's password in the Keychain (or an obfuscated file)

- New `chief.secrets_password-save [file]`: type a secrets file's password once and Chief stops prompting for it. Load, edit and `--rekey` use it, for both Ansible Vault and GPG.
- **Interactive only.** The password can only be typed at the command's prompt, never as an argument, environment variable or piped input, so it never sits in shell history or a hand-written file. It's checked against the file before it's saved.
- **Where it's kept:**
  - **macOS:** the login Keychain. The password reaches `security` on stdin, never on its command line.
  - **Linux desktop:** the keyring through `secret-tool` (libsecret), when a keyring service is running.
  - **Elsewhere** (headless servers, no keyring): `~/.chief_secrets-store/` (folder 700), AES-256 with a random key kept beside it (600). Chief says plainly that this is obfuscation, not protection from someone who can read your account.
  - `--store=keychain|file` overrides the automatic choice.
- **Order:** a password file env var (`ANSIBLE_VAULT_PASSWORD_FILE` / `CHIEF_SECRETS_PASSWORD_FILE`) still wins, then the saved password, then a prompt. Ansible Vault gets the saved password through a pipe, so no password file is written.
- `chief.secrets_password-status [file]` shows where the password will come from and which keychain is available. `chief.secrets_password-remove [file]` forgets it.
- If a saved password stops working (the file's password changed elsewhere), load and edit say so and show how to save or remove it. `--rekey` updates a saved GPG password automatically. For Ansible Vault, which asks for the new password itself, it removes the outdated one and tells you to save the new one.
- Help text: the "Password" sections of `chief.secrets_file-edit -?` and `chief.secrets_file-load -?` list the three sources in order.
- Tests: `tests/secrets-tests.sh` covers the file store (modes, no clear text, load without a prompt, precedence, status, remove, re-key updating it, a stale saved password), a throwaway macOS keychain, Ansible Vault through the pipe, and saving refusing to run without a terminal. The Linux keyring path isn't covered by automated tests.

### Secrets: change a file's password (`--rekey`)

- New `chief.secrets_file-edit [file] --rekey` changes the password of an existing secrets file without opening the editor. It works for both backends: Ansible Vault (through `ansible-vault rekey`) and GPG.
- It asks for the current password, or reads `ANSIBLE_VAULT_PASSWORD_FILE` / `CHIEF_SECRETS_PASSWORD_FILE`, then the new one twice. The two entries must match and can't be empty. `--new-password-file=PATH` reads the new password from a file instead, for scripts.
- GPG: the decrypted content goes straight from decrypt to re-encrypt and is never written to disk. The re-encrypted file replaces the original only when both steps succeed, and keeps its permissions. A wrong password or any other failure leaves the original untouched.
- If a password file supplied the current password, Chief reminds you to update it afterwards, because it still holds the old one.
- `--load` after `--rekey` loads the file with the new password.
- Tests: new `tests/secrets-tests.sh` re-keys real GPG and Ansible Vault files, checks the new password opens them and the old one doesn't, and checks that a wrong password changes nothing. Each backend is skipped when its tool isn't installed.

### Plugin links whose target is missing: warn, keep loading

- A user plugin can be a symlink into a checkout that only some machines have (for example a plugin in a shared plugins repo that links into a separate checkout servers don't have). Chief used to skip such a plugin silently, so you couldn't tell an intended absence from a broken link.
- Chief still skips it and keeps loading, but interactive shells now show a yellow warning naming the plugin and where its link points, with the command to silence it: `chief.plugin disable <name>`. `chief.reload` lists it as `missing:` next to the loaded and `off:` plugins. Scripts and other non-interactive shells stay quiet.
- Disabling the plugin on machines where it's meant to be absent marks it as intended and silences the warning.
- Tests: `tests/plugin-tests.sh` loads Chief with a broken plugin link in interactive, non-interactive and disabled cases.

### Old Bash in non-interactive shells: quiet, core-only load

- On macOS, tools that run the system Bash 3.2 non-interactively (scripts, editors, AI coding tools running `/bin/bash -c ...`) loaded every plugin. Each command printed the Bash warning and a batch of `declare: -A: invalid option` errors. Switching to a newer Bash isn't possible there: re-running it would drop the command being run.
- Chief now loads only its core library in that case, quietly: no warning, banner, plugins or SSH keys. Interactive shells are unchanged: they still warn and show how to switch to a newer Bash.
- Tests: `tests/bash-version-tests.sh` loads Chief in a real non-interactive and a real interactive shell under a simulated Bash 3.

### Documentation fixes

- Fixed: `chief.update` printed "Proceeding..." twice after you answered yes. The yes/no prompt already says it. The force-update confirmation no longer repeats it either, and now just warns "Force update: local changes will be lost."
- Fixed: the docs told you to run `chief.config_update`, which doesn't exist (the command is `chief.config-update`), and `chief.config_show`, `chief.version` and `chief.etc_confirm`, which never existed. Copying them failed with "command not found". The config examples now read the file directly (`grep "^CHIEF_CFG_" "$CHIEF_CONFIG"`), and the others point to `chief.status` and `chief.etc_ask-yes-or-no`.
- Fixed: many examples still used old underscore names (for example `chief.etc_copy_dotfiles`, `chief.oc_approve_csrs`, `chief.plugins_root`); the user guide and plugin guide also listed commands that don't exist (`git.branch_clean`, `ssh.key_add`, `chief.aws_s3_sync` and others). They now use the real names. The `chief.plugins_root` hint printed by Chief itself is fixed too.
- Configuration reference: added `CHIEF_CFG_VERBOSE`, `CHIEF_CFG_BASH_WARN`, `CHIEF_CFG_DEFAULT_EDITOR_PATH`, `CHIEF_CFG_EDITOR_GUI_CMD` (Cursor/VS Code for `--code`), `CHIEF_CFG_GIT_COMMIT_WARN_MB`, `CHIEF_CFG_DEV_TOOLS` and `CHIEF_CFG_PLUGIN_TEMPLATE`.
- Website home page and user guide: added `chief.status`, `chief.plugin enable|disable|status`, `chief.ssh_load-keys`, `chief.ssh_status`, `chief.ssh_host-key`, `chief.oc_status` and `chief.ssl_renew-tls-cert`; marked the AWS, OpenShift and Vault plugins as off by default, with how to turn them on; SSH key auto-loading is described as opt-in.
- Fixed plugin function counts in the README and on the website home page (System Utilities 17, OpenShift 10, SSL/TLS 5).

### Banner: configurable indicators, a secrets indicator and a compact logo

- New `CHIEF_CFG_BANNER_INDICATORS` (in the template's BANNER section) picks the status items shown to the right of the logo, and their order: `alias plugins tracking secrets` by default. Remove a name to hide it, or set `""` for just the logo and version.
- **The banner stays the same size,** so it still fits small screens. Indicators fill the logo's lines and line up in one column, bottom-aligned next to the version as before. Extras share the last line after a ` · `, and an indicator with nothing to show (like `alias` with no alias set) takes no line.
- **New `secrets` indicator:** `secrets: loaded`, `loaded (2)`, `loaded, silent` (a `--quiet` load, in yellow) or `not loaded`. At start-up it says `found`, since `~/.bash_profile` loads secrets after the banner prints. `chief.status` has the details.
- **Clearer `plugins` indicator:** `plugins: git [auto-update disabled]` showed "disabled" in red, which read as if your plugins were off. It now says what's loaded and where from, for example `plugins: 22 on, 4 off · git, manual update`. Auto-update is shown in green when on and neutral when off, since off is a normal choice.
- **New `CHIEF_CFG_BANNER_STYLE=compact`:** a 3-line, 13-column logo (box-drawing characters) that leaves about 12 more columns for the indicators. The indicators sit beside the logo's three lines and the version goes underneath, so the compact banner is 4 lines. `full` (the classic logo) stays the default.
- `chief.status`'s secrets section is shorter too: the file path on its own line, then `loaded automatically from ~/.bash_profile at 08:18:59 · gpg · password: keychain · silent (--quiet)`.
- `CHIEF_CFG_BANNER_SHOW_PLUGINS` / `CHIEF_CFG_BANNER_SHOW_TRACKING` leave the template. An explicit `false` in an older config still hides that indicator.
- Help (`chief.config -?`, `chief.config-set -?` and `--list`), the configuration docs (new "Banner indicators" section) and tests are updated. The tests cover the default, a custom list, an empty list, the legacy switch, packing extras, the compact style, the plugins text and the secrets indicator.

### Secrets: see what this shell loaded, and how

- Chief now records every secrets load in the shell: which file, when, the backend, where the password came from (password file, saved Keychain/file password, or prompt), and how the load started. It also flags a `--quiet` load as **silent**. Silent loads and loads made by your start-up files are no longer invisible.
- **How it started**, read from the call stack: *manually* (typed at the prompt), *automatically, from ~/.bash_profile* (or another start-up file or script), *by <function>* (for example a plugin), or *by secrets_file-edit --load*.
- **Where you see it:**
  - `chief.status` has a new **Secrets** line: "none loaded in this shell (available: …)", or each loaded file with how it was loaded.
  - `chief.secrets_password-status` has a "This shell:" line.
  - The start-up/reload hint about your shared secrets file says how it was loaded, instead of always "not applied to this shell yet".
- The record belongs to the current shell and survives `chief.reload`. If the secrets plugin is off, `chief.status` says so.
- Tests: a manual load, a quiet load from a start-up file, the record surviving a plugin reload, `chief.secrets_password-status` and `chief.status`.

### CI: macOS tests use a supported Bash

- The macOS CI job ran its tests with the runner's built-in `/bin/bash` 3.2, which Chief doesn't support. It now installs Homebrew Bash and fails early if the Bash it runs isn't 4 or newer, so macOS CI tests Chief the way it's meant to run (with BSD tools such as `sed`). The Linux job already used Bash 5.
- Chief's start-up warning for Bash older than 4.0 is unchanged; its tests simulate the old version and don't need a real Bash 3.2.

## 📋 Upgrade Notes

- **Banner:** run `chief.config-update` to add `CHIEF_CFG_BANNER_INDICATORS` and `CHIEF_CFG_BANNER_STYLE` to your config. Until then you get the default indicators. Your existing `CHIEF_CFG_BANNER_SHOW_*` lines keep working; only an explicit `false` hides anything.
- **`chief.etc_spinner` now returns the command's exit code.** It used to always succeed. If a script or plugin runs with `set -e` (or checks `$?` after the spinner) and relied on that, a failing command now stops it or reports failure. To keep the old behavior where needed, add `|| true`:
  ```bash
  chief.etc_spinner "Working..." "some_command" result || true
  ```
  (`result` is the name of a variable, given without `$`, that receives everything the command printed; use it afterwards as `$result`.)
- **Update branch:** existing configs keep their pinned `CHIEF_CFG_UPDATE_BRANCH` (for example `"main"`), so nothing changes until you opt in with `chief.config-set update_branch auto`.
- **Old Bash, non-interactive:** a script that sources Chief under Bash older than 4.0 without a terminal (for example macOS's `/bin/bash -c ...`) now gets only the core library, not plugins. If a script needs plugin commands, run it with a newer Bash: start it with `#!/usr/bin/env bash` and put Homebrew's Bash first in `PATH` (`brew shellenv` does this).
- Prefer the old spinner look? Add `--legacy`: `chief.etc_spinner --legacy "Working..." "some_command" result`.
